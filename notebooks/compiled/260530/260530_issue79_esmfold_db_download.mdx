### Objective

Many folded structures for protein hashes are found on s3://esm-protein-atlas/v1/folds/

The purpose of these downloads is to avoid rerunning folding experiments on sequences that have already been folded.

## 0. Deps

Versions used for this analysis. The same set was installed on the EC2 box that ran the download —

# Step 2: Plan for the Script

1. Compute MD5 hashes for all 4.7M sequences → list of protein_hash values
2. Query folds_1B.lance directly filtering by those hashes using the  → get structure_blob
3. Decode and save as PDB files

This work is done in `resources/260530_issue79_esmfold_db_download/esm_atlas_download.py`.

To run this, use an EC2 VM. For this analysis, I used a c7i.4xlarge.

Note: the script outputs directly to S3, so credentials are needed.

### Step 2a: Running the downloader

All of this runs **on the VM** (c7i.4xlarge), not in this kernel. Setup on a fresh box:

```bash
pip install pylance==7.0.0 pyarrow==24.0.0 brotli==1.2.0 msgpack==1.1.2 \
            numpy==2.4.6 zstandard==0.25.0 boto3==1.43.56 tqdm==4.68.2

# credentials are needed ONLY for the write to our own bucket -- the Atlas reads and the
# petadex FASTA read are both anonymous
aws configure set aws_access_key_id <your-access-key-id>
aws configure set aws_secret_access_key <your-secret-access-key>
aws configure set aws_session_token <your-session-token>   # if using temporary STS credentials
aws configure set default.region us-east-1
```

The script streams the input FASTA directly from `s3://` (and transparently handles `.zst`), so the
100+ GB ORFs file never has to land on the VM's disk.

**1. Hit-rate benchmark** — `--count` queries `protein_hash` only and reports the Atlas hit rate; it
never pulls a `structure_blob`, which is why a 1M-ORF probe finishes in ~20 min. The two runs in the
Results section below are two independent draws (change `--seed` between them):

```bash
ORFS=s3://petadex/logan/petadex.catalytic_orfs.v1.1.fa    # PETadex V1 -- swap for V2

python3 esm_atlas_download.py $ORFS --count --sample 1000000 --seed 0
python3 esm_atlas_download.py $ORFS --count --sample 1000000 --seed 1
```

**2. Full download → S3** — the real run. Defaults supply the rest (both datasets, `atlas` first;
4000 hashes per indexed query):

```bash
python3 esm_atlas_download.py $ORFS \
    --orf-map orf_hash_map.tsv.zst \
    --s3 s3://petadex-protein-structures/esmatlas/ \
    --format cif --workers 16 \
    2>&1 | tee esmatlas_download.log
```

`--orf-map` writes the complete `orf_id -> protein_hash` index as it streams (memory-flat, so it
scales to the full file). That is what makes *"which ORFs have a structure?"* a later join of this
index against `tracker.csv`'s `protein_hash` column, rather than a second pass over the Atlas.

**3. Resuming.** `tracker.csv` is the resume ledger: appended as batches complete, mirrored to
`<prefix>/tracker.csv` every ~5 min and at exit, and seeded back from S3 on a fresh box — so a
re-run after an interruption skips what is already done. Once `--orf-map` has been banked, reuse it
instead of re-parsing the FASTA:

```bash
python3 esm_atlas_download.py --hashes-from orf_hash_map.tsv.zst \
    --s3 s3://petadex-protein-structures/esmatlas/ --workers 16
```

Other flags: `--datasets 1b` (skip the 6.6M representative set), `--s3 ''` (write locally instead of
uploading), `--outdir`, `--format pdb`.

### Step 2b: Script Update — output layout now matches the ESMFold2 predictor (updated 2026-07-29)

The downloader writes, per unique sequence (keyed by `protein_hash = md5(sequence)`), the **same
three outputs that `esmfold2_local_predictor.py` writes** (issue #6), so an Atlas structure and a
freshly-folded one are interchangeable downstream — same filenames, same JSON shape, same ledger
columns.

**S3 layout** — default sink `s3://petadex-protein-structures/esmatlas/` (`--s3 ''` to write locally instead):

```
s3://petadex-protein-structures/esmatlas/
├── structures/<hash>.cif     # all-atom coords (atom37 → mmCIF); per-residue pLDDT in the B-factor
├── metrics/<hash>.json       # run block + scalars + per_residue_plddt + pae, one file per structure
└── tracker.csv               # the scalar ledger — resume table; mirrored to S3 + seeded back on resume
```

> **Changed 2026-07-29.** This was previously `structures/ + arrays/<hash>.npz + metrics.csv`. The
> npz is gone: per-residue pLDDT and PAE moved into `metrics/<hash>.json` (rounded to 2 dp, matching
> the cif B-factor precision), and `metrics.csv` became `tracker.csv` with the predictor's column
> set. Changed **before** the full run, so there is no old-format data to migrate.

**`tracker.csv` columns** — identical to `TRACKER_COLS` in `esmfold2_local_predictor.py`:

```
id, run_label, esmfold2, esmc, seq_len, protein_hash, truncated,
wall_s_median, residues_per_s, mean_plddt, ptm, iptm, status, error
```

The Atlas is content-addressed and has no notion of a PETadex ORFid, so `id == protein_hash` here
(the predictor keys `id` by ORFid instead). **Both write the same `protein_hash` column**, so that is
the column to join on. Fields the Atlas cannot supply are null/empty rather than invented: `esmc`,
`wall_s_median`/`residues_per_s` (these were folded by Biohub, not by us), `iptm` (single chains).
`run_label` records which Lance dataset the row came from (`folds_atlas.lance` / `folds_1B.lance`) —
that is where the old `source_dataset` column went. There is no `has_pae` column any more; test
`confidence.pae is not None` in the JSON.

**Quality metrics retained** — earlier versions kept only pLDDT (in the CIF B-factor) and **discarded pTM and PAE**:

| datum | where it lands | notes |
|---|---|---|
| per-residue pLDDT | CIF B-factor + `json:confidence.per_residue_plddt` | 0–100; from the `structure_blob`'s `confidence` field |
| mean pLDDT | `tracker.csv:mean_plddt` + `json:confidence.mean_plddt` | chain average |
| pTM | `tracker.csv:ptm` + `json:confidence.ptm` | from the Atlas `ptm` column |
| PAE | `json:confidence.pae` (`[L, L]`, `null` if absent) | from the Atlas `pae` column |
| provenance | `tracker.csv:run_label` + `json:run.dataset` | which Lance dataset the row came from |

Scalars are serialized *before* the per-residue/PAE arrays in each JSON, so a `Range: bytes=0-4095`
GET reads `mean_plddt`/`ptm`/`seq_len` without pulling the whole object.

**Gotcha (confirmed on a live row):** per the schema above, `pae` and `per_residue_plddt` are `binary` columns — each is a serialized **`np.savez` blob** (a zip whose member is `arr.npy`), *not* a list. `_coerce_pae()` `np.load()`s those bytes → `[L, L]`. pLDDT is taken from the `structure_blob`'s `confidence` field, so only the `pae` column needs this special decode.

**Verified end-to-end** on `test.fa` (`MNAKWITPVVTAFDAEGHVD`, 20 aa): reconstructed sequence matches, CIF B-factor == pLDDT (mean 71.33 == the ledger's `mean_plddt`), PAE decodes to `(20, 20)` with the expected near-zero diagonal rising off-diagonal.

**Layout re-verified 2026-07-29** by driving a synthetic Atlas row through `download()`: `tracker.csv`
columns compare equal to the predictor's `TRACKER_COLS`; the metrics JSON's key tree is identical to
the predictor's `build_metrics()` outside the intentionally producer-specific `run` block (whose
shared keys — `label`, `esmfold2`, `esmc`, `num_loops`, `num_sampling_steps`, `num_diffusion_samples`,
`seed`, `dtype` — are all present, `null` where the Atlas doesn't publish them); and resuming from an
existing `tracker.csv` skips finished hashes without duplicating rows or re-writing the header.
